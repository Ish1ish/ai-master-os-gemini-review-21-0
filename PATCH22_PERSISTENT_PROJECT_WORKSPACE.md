# PATCH22 — Persistent project workspace

## Purpose

PATCH22 adds SQLite-backed project continuity to the governed S21/O45 path. It creates a long-lived workspace from an existing PATCH21 plan result and supports later reads and progress mutations without regenerating the plan each time.

The workspace database is stored at `<AI_OS_UNIFIED_RUNTIME_PERSISTENCE_ROOT>/project_workspace.sqlite3`. If no custom root is configured, the same root resolution used by the S21 launcher applies.

## Workspace lifecycle

### 1. Save a generated plan

Submit an O45 intent with:
- action: `update_project_workspace`
- tool: `provider.project.workspace.write`
- payload operation: `create_from_plan`
- payload `project_id`: the same `project_id` used for the governed run
- payload `plan_result`: the full result from `provider.project.plan`

Submitting creates the intent but does not write SQLite. Explicitly execute the returned intent through `POST /api/intents/{intent_id}/execute`. A new workspace starts at revision 1, status `ACTIVE`, with milestone tasks and next actions normalized to stable task IDs.

Creation is idempotent for the same project ID and same plan fingerprint. If that project ID already holds a different plan, the tool returns `CONFLICT`; it never silently overwrites existing project state.

### 2. Read a workspace

Use action `read_only_inspection` with tool `provider.project.workspace.read`.
- `operation=get`: read the workspace and recent event history for the current runtime project ID
- `operation=list`: list workspace summaries owned by the authenticated requester

Reads are side-effect-free and safe to retry. The runtime stamps the authenticated requester onto the tool payload; caller-supplied owner IDs are overwritten.

### 3. Update progress

Use action `update_project_workspace` with tool `provider.project.workspace.write`. Every mutation except creation must include `expected_revision` from the last returned workspace result.

Supported operations:

- `update_task`: provide `task_id` and status `TODO`, `IN_PROGRESS`, `BLOCKED`, `DONE`, or `SKIPPED`; an optional note records the latest task context
- `append_note`: add progress, blocker, observation, or follow-up notes; optionally associate the note to a task
- `record_decision`: append a titled decision and rationale with optional known source IDs
- `update_status`: set `ACTIVE`, `PAUSED`, `COMPLETED`, or `ARCHIVED`

Stale revisions return `CONFLICT` and do not overwrite newer work. A project cannot be marked `COMPLETED` until every task is `DONE` or `SKIPPED`. Completed projects cannot have tasks reopened until the project is explicitly reopened; archived projects are frozen.

## Continuity and audit trail

Every successful workspace creation or mutation updates a revisioned JSON snapshot and appends a SQLite event with its revision, event type, bounded event payload, and timestamp. The response includes:
- the full workspace snapshot and plan
- source map
- normalized task list and progress counters
- notes and decision records
- recent event history

Task progress is calculated from the persisted task statuses, not generated by the model. The database is initialized lazily and each call opens and closes its own SQLite connection.

## Ownership and scope

A workspace is owned by the authenticated requester who creates it. Read/write handlers enforce owner matching; foreign-owned workspaces look like not-found. The runtime checks that a workspace read or mutation is bound to the same `project_id` as the governed run, and only the exact action/tool pairs are allowed:
- `read_only_inspection` + `provider.project.workspace.read`
- `update_project_workspace` + `provider.project.workspace.write`

The workspace mutation action is classified as a reversible medium-risk internal operation. O45 still governs execution. The submit call does not mutate state; the caller must explicitly drive the intent. No tasks, purchases, public content, external messages, or integrations are executed by this patch.

## Evidence boundary

Plan sources are URL-validated and normalized; source IDs in budget items, assumptions and risks are checked against the persisted source map. This does not prove semantic entailment or current accuracy. Workspace and plan outputs keep `decision_grade_evidence=false`; the operator must inspect cited pages and validate assumptions before material business decisions.

## Targeted tests

`tests/test_patch22_persistent_project_workspace.py` covers SQLite persistence across store instances, idempotent create/conflict, revision checks, task progress, notes and decisions, citation validation, completion/archive rules, owner isolation, and governed execution. `tests/test_s21_http_composition.py` asserts workspace tools are registered with correct retry policy.

Per the project workflow, focused PATCH22 and S21 composition tests should be run before merge; the lengthy full-regression suite is not a blocker for every incremental patch. No local execution or live provider test is claimed in this document.
